## 一、读不懂的几个「架构词」

| 术语 | 原来的定义 | 我的中文解释 |
|---|---|---|
| 聚合（Aggregate） | 领域中一组关联对象的边界，是数据修改的最小单元 | 一个「必须一起改」的对象小组。比如问题和它的回答、投票不是一个聚合；但一个问题 + 它的采纳状态 + 悬赏就是一个聚合。规矩是：外部只能通过这个聚合的入口方法改它，不能直接改里面的字段，否则不变式（比如「已采纳的回答必须属于该问题」）就会被绕过。 |
| 领域事件（Domain Event） | 领域中发生的、值得关注的事实 | 「已经发生、且别人会关心」的事实，用过去式命名：`QuestionPublished`、`AnswerAccepted`、`VoteCast`。它是通知、搜索索引这些副作用的触发点——主流程只管发事件，谁关心谁自己去听。 |
| 限界上下文（Bounded Context） | 领域驱动设计中的功能边界 | 一个词只在一个范围里有唯一含义的地方。本项目就是 `co-qa` / `co-reputation` / `co-discovery` / `co-user` 这几个 Maven 模块：`Question` 在 Q&A 里是聚合根，在 Discovery 里只是搜索索引里的一条文档，两边各说各的，不共用同一个类。 |
| Outbox 模式 | 用事务表保证领域事件最终发布的模式 | 想「改数据库」和「发消息」同时成功，但数据库事务管不到消息队列。做法是：把要发的事件先写进同一张 `outbox` 表、和业务改动同一个事务提交；再有个后台任务扫这张表把事件真正投出去。这样即使投递那一刻进程挂了，重启后还能补发，不会丢事件。 |
| 防腐层（Anti-Corruption Layer） | 隔离外部系统的适配层 | 外面系统的模型很难看（字段命名、概念都不一样），直接拿进来会污染我们的领域模型。所以中间加一层翻译：外部 DTO → 翻译 → 自己的领域对象。要换外部系统时只改这一层。 |
| 搜索索引（Search Index） | 为快速搜索建立的倒排索引 | 「词 → 包含这个词的问题 id 列表」的映射表，MySQL 全文索引和 Elasticsearch 都是这个思路。本项目里它是一份**可以被重建的副本**：真数据在问题表，索引坏了就重放事件重建。 |

## 二、几个我一开始会误会的业务词

| 术语 | 我的理解（含边界条件） |
|---|---|
| 声誉（Reputation） | 不是「等级」，是可以被花掉的积分：投票、被采纳会加，发悬赏会冻结。所以声誉不能被前端随便改，只能由领域事件驱动变更。 |
| 悬赏（Bounty） | 提问者押上自己的声誉换回答。关键边界：**冻结**而不是扣掉；到期没人被采纳要退回；同一个问题不能重复叠加悬赏，否则积分会对不上。 |
| 采纳（Accept） | 只能由提问者本人（或管理员）对自己问题下的回答执行；一个问题只能有一个被采纳的回答；已采纳后再采纳别人要先撤销前一个。 |
| 未回答（Unanswered） | 是「零回答」这个状态，不等于「没有已采纳回答」——后者是「未解决」，两个筛选条件别混用。 |
| @提及（Mention） | 只认 `@昵称` 且昵称存在才发通知；自己 @ 自己、在自己问题下 @ 自己都不发，否则通知列表会被自己刷屏。 |
| 相关问题（Related Questions） | 靠标签相似度（Jaccard）排序，没有共享标签就不推荐。它不是「搜索」的替代品：搜索是用户给关键词，相关问题是系统按相似度推。 |

## 三、流程类

| 术语 | 我的中文解释 |
|---|---|
| 验收标准（Acceptance Criteria） | 一条能被机器或人**当场判定真假**的句子。「前端能跑」不算，「访问 /login 返回 200 且控制台无 error」才算。 |
| Gherkin | 用 `Given / When / Then` 写验收标准的固定句式，好处是测试和需求能用同一段文字。 |
| DoD（Definition of Done） | 团队约定「什么才叫做完」的清单。本项目的口径：代码合并 + 测试通过 + 文档更新 + 有人 review 过，缺一项就不算 Done。 |
| Sprint / Backlog | Sprint 是 2–4 周的时间盒；Backlog 是还没做的需求清单，按优先级排，不是垃圾桶。 |
