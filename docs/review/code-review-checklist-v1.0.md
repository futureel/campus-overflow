# 代码评审清单 v1.0（Code Review Checklist）

> 维护人：陈洲（SM）　适用仓库：`futureel/campus-overflow`
> 版本：v1.0（Sprint 3 首次发布）　评审基线：Java 21 / Spring Boot 3.4 / Maven 多模块 / React 18 + TypeScript / Checkstyle 10.21 / ESLint 10
>
> **使用方式**：每个 PR 至少由 **1 名非作者的团队成员**评审。评审者逐项核对，命中「阻塞项（🔴）」必须 Request changes；其余为建议项（🟡）。作者在所有自动化门禁通过、且获得至少 1 个 Approve 后才能合并。

---

## 0. 评审前的自动化门禁（不通过不进入人工评审）

- [ ] 🔴 CI 流水线全绿（后端 `test`/`verify`、前端 `typecheck`/`build`、镜像构建）。
- [ ] 🔴 Checkstyle 零违规：本地 `mvn -f backend/pom.xml validate` 通过。
- [ ] 🔴 ESLint 零错误、Prettier 格式检查通过：`npm run lint`、`npm run format:check`。
- [ ] 🔴 分支与 main 无冲突，已基于最新 main 同步（rebase 或 merge main）。
- [ ] 🔴 没有提交密钥、令牌、连接串、个人隐私等敏感信息；`*.local`、构建产物未入库。
- [ ] 🟡 领域层覆盖率不低于 `domain.coverage.minimum` 当前阈值，且未为凑数写无断言测试。

---

## 1. 设计与架构（对应 ADR 与 ArchUnit 适应度函数 FF-1 ~ FF-6）

- [ ] 🔴 **分层方向正确**：依赖只能由外向内（interfaces → application → domain），领域层不反向依赖外层；`ArchitectureTest` 全绿。
- [ ] 🔴 **领域层保持纯 Java**：domain 包内不出现 Spring/JPA/Jackson/Validation 等框架注解与类型（FF-1）。
- [ ] 🔴 **跨限界上下文只经对方 `*-api` 发布语言或集成事件**，不直接引用对方内部实现类（FF-2）。
- [ ] 🔴 上下文之间无循环依赖；表名遵循上下文前缀（`id_` / `qa_` / `rep_` / `dis_`）。
- [ ] 🔴 业务规则内聚在聚合/值对象中，应用服务只做编排与事务边界，不在 Controller 里写业务逻辑。
- [ ] 🟡 聚合边界、值对象不可变、聚合根引用方式合理；没有为图省事把跨聚合逻辑塞进一个大类。
- [ ] 🟡 重要设计取舍与既有 ADR 一致；若偏离或新增决策，已补充/更新 ADR 并在 PR 说明。

## 2. 功能正确性

- [ ] 🔴 实现满足对应 Story 的验收标准与领域测试表达的业务规则，没有绕过测试。
- [ ] 🔴 正确使用 `docs/错误码.md` 中的错误码与异常类型，HTTP 状态映射正确，不生造错误码。
- [ ] 🔴 边界条件已处理：`null`/空串/空白、集合为空、越界、超长、并发与重复提交。
- [ ] 🔴 事件消费与异步处理具备**幂等性**（唯一键或去重表），重复投递不会重复加分/重复通知。
- [ ] 🔴 事务边界正确：一个用例一个事务，跨资源/外部调用不被无谓包进数据库事务。
- [ ] 🟡 金额、积分、计数等使用正确类型，避免浮点误差；时间处理显式指定时区。

## 3. 测试

- [ ] 🔴 新增/变更逻辑有对应测试，且测试真正断言行为（不是只跑不断言、不依赖随机/顺序）。
- [ ] 🔴 **未修改既有测试的断言**来迁就实现；如确有冲突，已在 PR 说明并与教师确认（学术诚信红线）。
- [ ] 🔴 未通过 `@Disabled`、删除测试、`catch 后忽略` 等方式掩盖失败。
- [ ] 🟡 测试命名清晰表达场景与预期（Given/When/Then 或 方法名_条件_结果）；测试数据构造集中、可读。
- [ ] 🟡 一个测试只验证一个行为；外部依赖用 Testcontainers/替身隔离，测试可独立重复运行。

## 4. 代码质量与可读性

- [ ] 🔴 命名达意且符合规范：类 `UpperCamelCase`、方法/变量 `lowerCamelCase`、常量 `UPPER_SNAKE_CASE`（测试代码的框架豁免见 checkstyle-suppressions）。
- [ ] 🔴 无未使用导入、变量、死代码与被注释掉的代码块；无 `System.out.println` 残留（用日志框架）。
- [ ] 🟡 函数短小、职责单一，圈复杂度可控；深层嵌套已用提前返回/卫语句简化。
- [ ] 🟡 无明显重复逻辑，恰当复用；魔法数字/字符串提取为具名常量。
- [ ] 🟡 注释解释「为什么」而非复述「做什么」；公共 API 有必要的 JavaDoc/TS 注释。

## 5. 安全

- [ ] 🔴 写操作具备正确的认证与授权检查，遵循最小权限；越权访问返回 403 而非泄露数据。
- [ ] 🔴 所有外部输入经校验；用户内容做 XSS 转义/净化（Markdown 用 OWASP sanitizer），前端不使用 `dangerouslySetInnerHTML` 渲染未净化内容。
- [ ] 🔴 不拼接 SQL（走参数化/Repository），不把用户输入拼进命令、路径或脚本。
- [ ] 🔴 CSRF 防护链未被关闭；安全相关配置（CORS、安全头、会话）未被随意放宽。
- [ ] 🟡 错误信息不向客户端暴露堆栈、SQL、内部地址等实现细节。

## 6. 可观测性与异常处理

- [ ] 🟡 关键路径有恰当日志：级别合理、带上下文、不打印敏感信息与大对象。
- [ ] 🟡 异常被具体处理或向上抛出，不吞异常、不捕获 `Exception` 后空处理。
- [ ] 🟡 涉及监控/告警的关键业务量已通过 Micrometer 指标暴露，命名遵循 `co_` 前缀约定。

## 7. 文档与交付

- [ ] 🟡 公共接口/配置变更已同步更新接口文档、README、错误码或运维/部署文档。
- [ ] 🟡 PR 描述包含：做了什么、为什么、如何验证（截图/命令/测试）、是否有破坏性变更与待办。
- [ ] 🟡 PR 粒度合理、关联对应 Issue/看板卡，标签与 Sprint 标记正确。

---

## 8. 评审结论与礼仪

| 结论 | 适用情形 |
| --- | --- |
| **Approve** | 无阻塞项，建议项可后续处理。 |
| **Request changes** | 存在 🔴 阻塞项，或有必须澄清的设计/正确性问题。 |
| **Comment** | 仅讨论、暂不结论，适合开放问题。 |

- 评审对事不对人：指出问题并给出理由与建议，避免主观否定；作者对每条意见明确回应（采纳/解释/另开卡）。
- 讨论分歧先在 PR 内澄清，必要时拉 SM/PO 或在站会、回顾会达成一致，不私下合并。
- 合并遵循分支保护与「所有代码走 PR、不直推 main」；合并后确认相关 Issue/看板状态已更新。

> 本清单随团队实践持续演进：新增的高频问题在回顾会提出后，更新到下一版本并记录变更说明。
